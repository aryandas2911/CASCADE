1. INTRODUCTION & PURPOSE
================================================================================

Document Purpose

This document describes the complete architecture and technical design of Cascade.

It defines the responsibilities, interactions, interfaces, data flow, internal algorithms, scalability characteristics, and failure handling mechanisms for every major subsystem.

The goal is to provide sufficient technical detail for another engineer to understand, implement, extend, or maintain the platform without relying on undocumented assumptions.

Vision

Cascade is a production-grade distributed execution engine for AI workflows. It executes DAG-based workflows while optimizing latency, cost, throughput, and reliability through scheduling, routing, caching, checkpointing, batching, replay, and observability.

The platform is infrastructure—not an application.

Goals

- Execute arbitrary DAG workflows
- Distributed worker execution
- Adaptive scheduling (heuristics and cost models)
- Multi-provider model routing
- Checkpointing and crash recovery
- Intelligent caching
- Speculative execution
- Replay/debugging
- Full observability
- Benchmarking
- Modular architecture
- SDK and REST/gRPC APIs

Non-Goals

- Training foundation models.
- Reinforcement-learning scheduler (initial architecture uses heuristics/cost models).
- Multi-region deployment.
- Kubernetes-first architecture.

3. ARCHITECTURAL DECISIONS & PRINCIPLES
================================================================================

System Constraints

The runtime is designed under the following architectural constraints:

- Workflows must be Directed Acyclic Graphs (DAGs).
- Workers are stateless.
- PostgreSQL is the system of record.
- Redis provides transient messaging only.
- Every task must be idempotent.
- External AI providers are treated as unreliable services.
- Execution must tolerate partial failures.
- Long-running workflows must survive process restarts.
- Every execution decision should be observable.

These assumptions influence every subsystem described below.

Major Technology Decisions

Language
- Python: Primary language for orchestration, AI ecosystem, rapid iteration.
- Rust (optional): Performance-critical scheduler/worker components if profiling justifies it.

Communication
- gRPC + Protocol Buffers: Chosen for efficient typed service communication, streaming, and language interoperability. Rejected REST for internal RPC due to serialization overhead.

Workflow Representation
- Directed Acyclic Graph (DAG): Enables dependency analysis, parallel execution, critical-path optimization, replay and scheduling.

Scheduler
- Adaptive heuristic scheduler instead of RL. Uses latency, estimated cost, queue depth, retries, dependency depth and resource availability. Reason: deterministic, explainable, easier to benchmark.

Worker Queue
- Redis Streams (initially): Simple, reliable, consumer groups, persistence, local development. Kafka can be evaluated later if throughput requires it.

Database
- PostgreSQL: Stores workflow definitions, execution metadata, checkpoints, audit logs, routing history. ACID guarantees and mature indexing.

Cache
- Redis: Fast in-memory cache for prompt hashes, execution results, workflow metadata.

Checkpointing
- Persistent checkpoints stored in PostgreSQL/object storage. Supports resume after failure and partial recomputation.

Model Routing
- Strategy pattern. Policies: Lowest latency, Lowest cost, Highest quality, Balanced, User-defined

Observability
- OpenTelemetry, Prometheus, Grafana. Reason: industry standard tracing, metrics, dashboards.

Containers
- Docker Compose for development.
- Kubernetes only after architectural maturity.

Engineering Trade-offs

- Explainability over black-box optimization.
- Reliability over peak benchmark numbers.
- Incremental optimization over premature complexity.
- Composition over monolithic architecture.

Decision Matrix

Decision             Chosen                Alternative      Why
---------------------------------------------------------------------------
Queue               Redis Streams         Kafka            Simpler deployment and sufficient guarantees for initial scale
Internal RPC        gRPC                  REST             Lower overhead and strong typing
Database            PostgreSQL            MongoDB          Strong consistency and relational workflow metadata
Workflow Model      DAG                   General Graph    Easier validation and deterministic execution
Scheduler           Heuristic             RL               Predictable, explainable, and achievable within project scope
Worker Model        Stateless             Stateful         Easier recovery and horizontal scaling
Cache               Prompt Hashing        Semantic Cache   Deterministic behavior and lower complexity
